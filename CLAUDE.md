# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Commands

- `npm run web` / `npm run ios` / `npm run android` — start the Expo dev server for a given platform (`npm start` lets you pick a platform interactively).
- `npm run lint` — ESLint via `expo lint` (flat config in `eslint.config.js`, extends `eslint-config-expo`).
- `npx tsc --noEmit` — type-check (no dedicated npm script for this).
- `npm run reset-project` — Expo's stock script to archive the starter app into `app-example/` and scaffold a blank `src/app/`. Not relevant day-to-day; only run if explicitly asked to reset the template.
- `npm test` — Jest via the `jest-expo` preset (config lives in `package.json`, not a separate file). See "Tests" below.

## Environment variables

Copy `.env.example` to `.env.local` (gitignored) and fill in real values. All are `EXPO_PUBLIC_`-prefixed so Expo inlines them client-side at build time:
- **No `EXPO_PUBLIC_TICKETMASTER_API_KEY`.** It moved server-side — see the concerts proxy below. It is a Supabase secret now (`supabase secrets set TICKETMASTER_API_KEY=...`). If it is still in your `.env.local`, delete it: nothing reads it, but Expo still inlines it into a build.
- `EXPO_PUBLIC_EDMTRAIN_API_KEY` — optional; `src/services/edmtrain.ts` returns `[]` until this is set.
- `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` — required for auth/saved-concerts/profile to work; `src/lib/supabase.ts` falls back to placeholder values and `isSupabaseConfigured` gates the UI when unset.

## Architecture

This is an Expo Router (file-based routing, `src/app/`) universal app targeting iOS, Android, and web (`web.output: "static"` in `app.json`), building an NYC EDM concert finder on top of the default Expo starter template.

**Dual tab-bar implementation.** `expo-router/unstable-native-tabs` (`src/components/app-tabs.tsx`) doesn't render on web, so there's a parallel web-only tab bar (`src/components/app-tabs.web.tsx`) built from `expo-router/ui`'s `Tabs`/`TabList`/`TabTrigger`. Both are bottom bars with icon+label, matching each other — the web one uses `expo-blur`'s `BlurView` for a translucent/frosted background (it used to float as a pill at the *top*; that was deliberately moved to the bottom to match native and fix a real overflow bug — see the web layout gotchas below). Both must be updated together when adding/removing a tab/route.

**Tabs are Home / Search / Explore / Settings**, all inside a `(tabs)` route group. Everything else — a show's own screen (`concert/[id]`), the Settings sub-screens, the legal pages, `reset-password`, `follow-picker`, the parked `ask` — is a *sibling* of that group rather than a child, so those routes open over the tab bar instead of inside it. That restructure is what made the legal pages reachable by URL at all: previously every route lived under the tab navigator, which only renders routes carrying a `Trigger`, so visiting `/terms` directly rendered the home screen.

Home (`index.tsx`) *is* the full concert list — it previously showed a featured carousel while a separate `/list` route showed the same shows as cards, which was near-duplicate, so the list took over the landing screen and `list.tsx` was deleted.

**`ask.tsx` is built but is not a tab** (2026-08-16). Its Edge Function was never deployed, so a tab led to a screen that could only fail; the owner then decided not to pursue the feature. The route, `use-ask.ts`, the Edge Function, and the migration all remain in the repo untouched — `ask.tsx` simply has no `Trigger`, joining `reset-password`, `privacy-policy`, and `terms` as directly-reachable-but-untabbed. **Nothing needs deploying for the app to work.** Re-adding the tab means restoring a trigger in *both* `app-tabs.tsx` and `app-tabs.web.tsx`, then completing the deploy steps in the Ask section below.

**Platform-split files.** Metro resolves `*.web.tsx` over `*.tsx` on web automatically. Used for: the tab bars above, `animated-icon.web.tsx`, `use-color-scheme.web.ts`, and the concerts map (`concerts-map.tsx` for native vs `concerts-map.web.tsx`/`concerts-map-leaflet.web.tsx` for web).

**SSR gotcha:** because `web.output` is `"static"`, Expo Router does a Node-based static render pass (even in dev) with no `window`/`document`. Any module that touches those at import time crashes every route. This bit both the Leaflet map (fixed by lazy `import()`-ing `concerts-map-leaflet.web.tsx` client-side only from `concerts-map.web.tsx`, gated on `typeof window !== 'undefined'`) and the Supabase client (AsyncStorage's web backend touches `window`; `src/lib/supabase.ts` wraps it in an SSR-safe storage adapter that no-ops server-side). Keep this in mind before adding any browser-only library.

**Theming.** `src/constants/theme.ts` is dark-only by design — `Colors.light` and `Colors.dark` intentionally share one palette (this is not an adaptive light/dark app; styled after TIXR/CrowdVolt: near-black surfaces, one accent color used sparingly for active/selected states and saves, a single `Radius` scale (`card`/`large`/`pill`) instead of ad hoc corner values). `useTheme()` (`src/hooks/use-theme.ts`) resolves it.

**Two accent tokens, and they are not interchangeable.** `theme.accent` (`#E03131`) is the **fill** — pill buttons, selected chips, the selected calendar day — with `theme.accentInk` (white) as the text on top of it. `theme.accentText` (`#EF4444`, the same red lightened) is for the accent used **as** a mark on the dark background: link text, the saved-heart icon, spinners, thin outlines, the carousel dot. The split exists because a fill colour and a text colour have opposite contrast requirements — measured on `background`, `accent` only reaches ~4.4:1 (below WCAG AA for the 14px text this app uses) while `accentText` reaches 5.3:1; conversely white-on-`accent` is 4.5:1 (passes) where white-on-`accentText` would not. Rule of thumb: **behind content → `accent`; on the dark background → `accentText`.** The one deliberate exception is the Leaflet concert pin (`concerts-map-leaflet.web.tsx`), which uses `accent` because it sits on *light* map tiles, not on the app's dark ground.

The palette was violet (`#8B5CF6`) until 2026-08-15. It moved to red because the reference designs the user kept pointing at (their own TIXR/CrowdVolt-style screenshots) use a red/coral accent on black, and because "purple and black" is a widely-recognised AI-generated-design tell. `backgroundSelected` was retinted warm (`#241F1F`) at the same time so raised surfaces sit in the accent's colour family. Note the old violet actually *failed* AA for white-on-accent (4.23:1), so this was an accessibility improvement as well as an aesthetic one. **The soft `Radius` scale was deliberately kept** — rounded corners are a native-mobile platform convention (and are all over the user's own reference screenshots); the "soft corner radius" critique targets `rounded-lg`-on-everything web design and doesn't transfer here. `ThemedText`/`ThemedView` (`src/components/`) are the standard building blocks — prefer them over raw `Text`/`View` with manual colors; `ThemedText type="eyebrow"` is the bold/uppercase/letter-spaced style used for section headers ("Buy Tickets", "Saved Concerts"). `ScreenScaffold` (`src/components/screen-scaffold.tsx`) is the shared scrollable-screen shell used by List/Settings — reuse it rather than hand-rolling the header+ScrollView pattern.

**Type scale and the display face.** `Fonts.size` / `Fonts.lineHeight` / `Fonts.weight` (`src/constants/theme.ts`) are one six-step scale (`xs` 12 → `xxl` 32) that replaced eleven ad hoc `fontSize` values scattered across components. Sizes live there and nowhere else — a raw number in a component is a new scale step nobody agreed to. `base` is 16 because that's the floor for mobile body text, at 1.5 leading; headings run tighter deliberately, since leading that helps a wrapped paragraph makes a two-line title read as two unrelated lines. Two `fontSize` values survive off-scale on purpose, commented at their sites: the save glyph in `concert-list-card.tsx` and `concert-detail-sheet.tsx`, each a single character optically centred in a fixed tap area where the line height is doing centring rather than typographic work.

**Archivo Expanded** (ExtraBold, width 125, `assets/fonts/`, 109KB, loaded via `useFonts` in `_layout.tsx`) is the display face, attached to `ThemedText`'s `title` and `subtitle` types. Wide and heavy reads as marquee signage, which is the subject; at body sizes it stops being characterful and just becomes hard to read. **This reaches further than "the two largest steps" suggests** — concert card titles use `subtitle`, so they render in the display face at 19px. That's deliberate: a show name on poster art is the most marquee-like text in the app. `_layout.tsx` gates its tree on the font because the face is much wider than the system fallback and swapping mid-render visibly re-lays-out the header; a decode error counts as ready, so a broken font degrades to system rather than hanging behind a splash.

**No icon fonts on web.** `app-tabs.web.tsx` used `expo-symbols`' `SymbolView`, whose web fallback pulled `MaterialSymbols_400Regular.ttf` — **940KB downloaded on every page view to draw four glyphs**, more than eight times the size of the app's actual display face. It's now `src/components/tab-icons.web.tsx`: four hand-written 24×24 SVG paths as data URIs on plain DOM `<img>` elements. Measured web font payload went 1160KB → 110KB. Two traps if you touch this: React Native's `<Image>` **silently fails** on an SVG data URI (renders the sized container with no background and no console error — the icons just vanish), so these use an intrinsic `<img>`, which is legitimate because React Native Web renders through React DOM and this is a `.web.tsx` that never reaches native; and `react-native-svg` is deliberately *not* a dependency — adding a whole renderer to draw four shapes isn't worth it. Native is unaffected: it uses real SF Symbols with no download.

**Night-density strip** (`src/components/night-density-strip.tsx`) replaced the old "‹ This Week ›" arrow row. Seven bars, one per night of the visible week, each sized by that night's show count — the arrows could page a week but never said what was *in* one. Tap a bar to filter to that night; tapping the selected one clears it. Chevrons or a horizontal drag page weeks (the `PanResponder` only claims a gesture once it's clearly horizontal, so vertical scrolling still works). Counts honour category and borough but deliberately ignore the selected date, or selecting a night would flatten every other bar to zero. Empty nights draw a stub rather than nothing — a dead night is information, and zero height reads as missing data. No animation: bars re-measuring on every filter change is motion carrying no information.

**Empty states must never claim zero shows when the dataset has them.** The home screen previously said "No upcoming EDM shows found right now" while 85 shows were loaded — today is often the last day of the Mon–Sun week and the feed only returns future events, so the default landing state was a blank screen making a false claim. `useConcertsFilters` now returns `hasAnyConcerts` and `nextShowAhead` so the empty state distinguishes no-data-loaded, quiet-week-with-shows-later, and filters-exclude-everything. A quiet week offers the soonest show as a one-tap jump. **Deliberately not auto-advancing** to that week on load: that's exactly what surprises someone who paged back to an empty week on purpose, and latching it to fire once makes it inconsistent.

**Visual design.** Image-forward cards: `ConcertListCard` renders concert poster art (`imageUrl`) with a bottom gradient overlay (`expo-linear-gradient`, values in `PosterGradient`) and falls back to a plain themed card when a concert has no image. `SkeletonCard`/`SkeletonCardRow` (`src/components/skeleton-card.tsx`) are pulsing placeholders shown instead of spinners while concert images load. `expo-haptics` fires a light impact on every save/favorite tap.

**Concerts data layer**, in dependency order:
`src/types/concert.ts` (`Concert`; `ConcertSummary` — the display-only shape shared by cards/the detail sheet/ticket links, i.e. everything except map coordinates and filter-only fields; `City`, `CITIES`, `Borough`; `SavedConcert = ConcertSummary`) → `src/services/{ticketmaster,edmtrain}.ts` (pure fetch-and-normalize per source, both return `Concert[]`; `ticketmaster.ts`'s `pickImageForWidth()` takes the **smallest image that still covers the target width**, not the largest — the array isn't sorted by size, so `images[0]` is often a 100px thumbnail, but always taking the largest overshot to 2426px sources (537KB measured) for a ~360pt card. Target comes from `PosterDisplayWidth × PosterImageScale` in `constants/theme.ts`; at 2× that lands on the 1024px rung, measured 2620KB → 864KB for a 9-show week. `PosterImageScale` is the one lever for poster quality vs bytes) → `src/hooks/use-edm-concerts.ts` (merges sources, dedupes via `dedupeConcerts()` — same show can come back as two listings, most commonly separate GA/VIP Ticketmaster "events" for one show, keyed on name+venue+exact start time so a multi-day festival, which has a different start time per day, still shows once per day rather than being collapsed — then sorts) → `src/hooks/use-concerts-filters.ts` (client-side category filtering — every category now answers from a real field or a real clock, none guess; also owns borough, distance, date, week and Following filtering — see below) → `src/components/{concerts-filter-bar,concerts-map,concert-list-card}.tsx` → the `explore.tsx`/`index.tsx` screens. Tapping a card or map pin opens `src/components/concert-detail-sheet.tsx` (a bottom sheet), which lists tappable ticket-source rows from `src/lib/ticket-sources.ts` — Ticketmaster gets the real link/price from the API response; Vivid Seats and AXS get a confirmed direct search link (`?searchTerm=`/`?q=` respectively — AXS's verified against a live `axs.com/search?q=` example); and SeatGeek/StubHub/Dice/CrowdVolt/TIXR get a domain-scoped web-search fallback (`site:seatgeek.com ...`) with a clearly-marked mock price, since none of those five have a verifiable direct search URL (TIXR actively 403s non-browser requests via DataDome bot protection, even on its homepage) — see the `TODO(real pricing)` comment there for what real integration would need per platform.

**The Ticketmaster feed is ~39% non-electronic, and `isLikelyElectronic()` (`ticketmaster.ts`) filters it at normalize time.** A `classificationName=Dance/Electronic` search matches loosely — the app was leading with **Harry Styles at Madison Square Garden**, whose residency alone was 30 of 85 listings. Neither classification field works alone, which is why this is a rule and not a field check:

- **`genre` alone fails**: the `Other` bucket holds Bicep, Black Coffee, San Holo, Jason Ross, DJ Pauly D, Kruder & Dorfmeister, NOTD, French 79, Nitzer Ebb. Narrowing to `Dance/Electronic` would discard ~10 real acts to catch 4 bad ones.
- **`subGenre` alone is actively wrong**: Hernan Cattaneo (progressive house), Desert Dwellers (downtempo) and DOMi & JD Beck (jazz) are all tagged `Amapiano`, and the same show returns `Other` on one listing and `Amapiano` on another.

So: block genres that are never electronic, **rescue** anything whose subGenre says otherwise, and leave `Other` alone entirely. **subGenre is only ever consulted to keep an event, never to remove one.** **Every classification is checked, not just `classifications[0]`** — Ticketmaster attaches up to four and the first is often the least representative (Harper leads `Jazz` but also carries `Dance/Electronic/Ambient`; DDXS leads `Rock` but also carries `Dance/Electronic/Experimental Electro`). The effective rule is *drop only when no classification is electronic*. Measured: 33 of 85 listings across 4 acts (Harry Styles, Bryson Tiller, Arlo, Teddy Riley). Deliberately permissive at the edge — Sid Sriram survives on one `Ambient` tag, because a missing show is harder to notice than an extra one.

**Residency grouping is designed but deliberately not built** (parked 2026-08-16). One act with many dates floods the list; Harry Styles' 30 listings was the severe case and the genre filter removed it *by accident*, so the problem is masked rather than solved — a real EDM residency (a 10-night Aoki run) would reproduce it. Measured after filtering: only 4 of 39 acts have >1 date, worst case 4 listings in one week (Galantis, Sid Sriram). **Revisit when an act exceeds ~5 dates in one week.** The agreed design: one card per **artist + venue** (a residency is one act in one room; the same act at two venues stays two cards), triggered at 2+ dates in the visible window, with the dates as **tappable chips rather than an expander** — no expand/collapse state, no animation, no reduced-motion branch, and every date stays one tap from its sheet. The night strip stays untouched, since grouping is display-only and 4 Galantis nights genuinely are 4 nights with something on. Open question deferred with it: the save heart has no meaning on a group (saves are keyed per show id) — the intended answer is to drop the heart from grouped cards and save from each date's sheet.

**Multi-city support.** `CITIES` (`src/types/concert.ts`) has six RA-Guide-style major US cities — Ticketmaster can query any of them today, but **NYC is the only one actually vouched for**; the rest are there so the switcher/preference are ready. Each screen (`explore.tsx`/`index.tsx`) still owns its own local `city` state independently (unchanged), but now seeds it from the signed-in user's `profiles.default_city` via `src/hooks/use-apply-default-city.ts` — a one-time effect (latched with a ref) that applies the saved default on first load without fighting a manual city switch made afterward. Users set the preference in Settings' "Default City" chip row, which calls `updateProfile({ defaultCity })`. **Times render in the venue's timezone, never the viewer's** (`src/lib/format-date.ts`). This is what the ticketing platforms do and it is deliberately *not* "show it in the user's local time": a 9pm Los Angeles show is 9pm, because that is what the ticket says and what you would tell a friend. Rendering it on a New York viewer's clock gives "12:00 AM" the *next day* — right about the instant, wrong about the event, and wrong about which night it is on. Every formatter takes an IANA zone; there is no viewer-timezone path on purpose, since two answers to "when is this show" is worse than one occasionally surprising one.

The zone comes from `Concert.timezone`, captured from Ticketmaster's **`_embedded.venues[0].timezone`** — measured present on 86/86 NYC and 100/100 LA listings, where the event-level `dates.timezone` was missing on ~20% of both, so prefer the venue field. `City.timezone` is only the fallback for a source that supplies none. `getConcertDateKey` is zone-aware for the same reason: a 9pm LA show is `04:00Z` the next day, so keying it off UTC files it under the wrong night and it vanishes from that day's filter and its bar in the night strip. `formatDateKeyLabel`/`dateKeyFor` stay zone-*un*aware on purpose — they are integer calendar arithmetic on a `{year, month, day}` triple, not instants. **`shouldShowTimeZone` gates a "PDT"-style suffix to the concert detail screen only**, shown when the viewer's clock disagrees with the venue's: stamping it on every list row is noise on the common case of browsing your own city, but omitting it entirely lets a cross-country time read as local on the screen where someone decides if they can make it. An unknown IANA zone falls back rather than throwing, since `Intl` raises a `RangeError` and a wrong hour beats a screen that will not render.

**Borough filtering.** `City.boroughs?: Borough[]` (`src/types/concert.ts`) is an optional list of named sub-areas — populated for NYC (Manhattan/Brooklyn/Queens/Bronx/Staten Island), left `undefined` for cities without well-known named sub-areas (e.g. Las Vegas). Each `Borough.boundary` is a **real GeoJSON MultiPolygon** from NYC Open Data's official "Borough Boundaries" dataset (Dept. of City Planning, dataset id `gthc-hcne`, water excluded, geometry simplified to ~174KB — see `src/data/nyc-boroughs.ts` and the raw `src/data/nyc-borough-boundaries.json`), not an approximated bounding box — `src/lib/geo.ts`'s `isPointInMultiPolygon` (standard ray-casting, handles holes) tests a venue's actual lat/lng against the real borough shape. No API exposes a borough field directly, so this still filters against the venue coordinates already fetched for the map, but the geometry itself is exact, government-sourced data, verified against known venues (Madison Square Garden→Manhattan, Barclays Center→Brooklyn, Yankee Stadium→Bronx, Citi Field→Queens, St. George Theatre→Staten Island all classify correctly) — unlike the category keyword matchers, this doesn't need re-verification as venues are added. `useConcertsFilters(concerts, city)` takes `city` as a second argument and owns `selectedBoroughId`/`setBoroughId` alongside `category`/date, resetting the borough selection when `city` changes — done by comparing `city.id` during render (not in a `useEffect`), so it doesn't need a `set-state-in-effect` eslint-disable. Boroughs are **not** a separate chip row — they're nested inside the city dropdown itself (New York → Manhattan/Brooklyn/Queens/The Bronx/Staten Island, indented under the city they belong to), so picking a borough sets both `city` and `selectedBoroughId` in one tap and the city pill's label switches to show the borough name instead. Tapping the parent city row clears the borough back to "all of this city." The dropdown (`cityMenu` style) has a `maxHeight` + `ScrollView` since with boroughs nested in it can run past a screen's worth of rows.

**Date filtering.** `ConcertsFilterBar` has a "Date" pill next to the city pill (both in a `pillsRow`, label defaults to today's date rather than a generic placeholder when nothing's picked) that opens `src/components/date-picker-sheet.tsx` — a real calendar-grid bottom sheet (month navigation, SUN–SAT day grid, today outlined, selection filled in `theme.accent`, "This Week"/"Next Week" quick-select, "Reset to Today"/"Apply") rather than a scrolling list, matching a native-calendar UX pattern. Selecting a date filters to concerts on that exact NYC-calendar day, compared via `getNycDateKey()` (an `Intl.DateTimeFormat` with `timeZone: 'America/New_York'` and `en-CA` locale for a direct `YYYY-MM-DD` string) so the comparison lines up with what's actually displayed, regardless of the viewer's own device timezone. The sheet re-stages its pending selection from the applied one every time it opens (compares a `wasVisible` state during render, not a `useEffect`) so a cancelled edit doesn't leak into the next open. Calendar grid math (which weekday the 1st falls on, days in month) intentionally uses local device time — it's just day-of-week/day-count arithmetic on a `{year, month, day}` triple, not a concert-instant comparison, so no timezone conversion is needed; `dateKeyFor()`/`formatDateKeyLabel()` in `src/lib/format-date.ts` build/format keys directly from those integers. The "This Week"/"Next Week" buttons don't close the sheet on tap — "Next Week" calls the same relative `goToNextWeek` stepper as the filter bar's own `‹ ›` row (see below), so repeat taps keep paging forward instead of landing on a fixed week, and a live "Showing: …" label inside the sheet gives feedback since the modal covers the filter bar's own week label while open.

**Default week/month scoping.** Opening the app doesn't dump every upcoming show — `useConcertsFilters` also owns a `weekOffset` (default 0) that scopes results to the *current* Monday–Sunday week by default, paged via a "‹ This Week ›" row in `ConcertsFilterBar` (shown between the pills row and the footer). Weeks are Monday–Sunday specifically so a weekend (Fri/Sat/Sun) never splits across two week windows — verified against `isThisWeekend`'s own Friday-anchor math, which now also shifts by `weekOffset * 7` days so paging weeks also pages "This Weekend." **Pop-ups is the one exception**: it's scoped to the current calendar month instead of a week (pop-ups are sparse enough that a week window often comes up empty), so the week-nav row hides itself when `category === 'Pop-ups'` (`weekNavRelevant` in the hook's return). Picking a specific date via the calendar sheet overrides the week/month window entirely (but still combines with category/borough) — the week-nav row also hides itself once a date is selected, since it wouldn't do anything. Paging is capped at `MAX_WEEKS_AHEAD` (8) so the "next week" arrow can't run away indefinitely, mirroring the date picker's 12-month cap on the same idea. `useConcertsFilters` ANDs `category` (+ its week/month window), `selectedBorough`, and `dateKey` together — this is all additive to the existing category filters (This Weekend/21+/Free/etc.), not a replacement for any of them.

**Filters dropdown.** The category chips (All/This Weekend/Day Parties/Late Night/Outdoors/21+/Free) are **not** a horizontal scrolling chip row — like the city/borough control, they're consolidated into one "Filters ▾" pill (third pill in `pillsRow`, alongside City and Date) that opens a dropdown list, current selection highlighted. Its menu (`filtersMenu` style) opens right-aligned (`right: 0`, not `left: 0` like `cityMenu`) since it's the rightmost pill — opening from the left edge would push it off-screen on a narrow phone.

**User location + distance.** `src/hooks/use-user-location.ts` wraps `expo-location`, but gates the real OS permission dialog behind the app's own soft-ask first (`src/components/location-permission-prompt.tsx`, a "Turn On Location"/"Not Now" sheet) — standard practice since the OS dialog is much harder to reverse than an in-app one if declined reflexively. **Only `explore.tsx` renders the sheet** (index.tsx calls the hook read-only, just to pick up coords if already granted, so switching screens before answering can't trigger a duplicate prompt). If declined or not yet granted, Explore shows a small "📍 Show My Location" pill (bottom-right of the map) to retry on demand.

What's persisted to AsyncStorage (`location-prompt-choice`) is the user's *choice* — `'declined'` (tapped "Not Now") vs `'requested'` (tapped "Turn On Location") — not a plain "have we asked" boolean, and that distinction matters: browsers offer a temporary "Allow once" grant that expires on reload, at which point `getForegroundPermissionsAsync()` correctly reports back to `'undetermined'`. A real granted/denied OS decision, or an explicit `'declined'` choice, suppresses the sheet; a lapsed "allow once" grant (`'requested'` on file but status back to `'undetermined'`) re-shows it automatically rather than silently doing nothing. `getCurrentPositionAsync` is also wrapped so a failed position fetch (timeout, `POSITION_UNAVAILABLE`) can't leave `hasPrompted` stuck at `null` forever — that would hide both the sheet and the retry pill with no way back in.

**⚠️ Location cannot work when the dev server is opened over the LAN, and this is not a bug.** Browsers expose `navigator.geolocation` only on a **secure origin** — HTTPS or `localhost`. Opening `http://<lan-ip>:8081` from a phone (the normal way to test on device) is refused outright: no dialog appears, the call fails, and it is *not* a permission the user can grant. Measured on the running server — `localhost:8081` → `isSecureContext = true`; `192.168.1.177:8081` → `false`. Every failure downstream was silent (`getCurrentCoords` swallows errors → `coords` stays null → `ConcertsMap` gets no `userLocation` → no blue dot, no explanation), which reads as a broken feature. `useUserLocation` now detects this **before touching the permission APIs** and returns `unavailableReason`; the map pill reads "Location needs https" and the full explanation goes to a `console.warn`, since the condition is dev-only and can't occur in an installed app. **This resolves itself on deploy** — any host serves HTTPS, and a native build isn't subject to secure-origin rules at all.

**`canAskAgain` exists because the retry pill was a dead end.** Once permission is hard-denied, the OS and browser both stop showing their dialog and silently resolve every request as denied — so tapping "Show My Location" did nothing and said nothing. The hook tracks `canAskAgain` and the pill switches to "Location blocked · Settings" rather than offering a retry that cannot work. A standing denial is also applied on load, not only after a failed request.

**The soft-ask waits 1200ms for the map to paint** (`mapSettled` in `explore.tsx`). It used to fire the instant the stored choice resolved from storage, which is fast enough that a sheet covered the screen before the map rendered — asking to show your location on a map, with no map visible behind it.

**The map pill offsets by `BottomTabInset`, not a bare `Spacing` value.** At `bottom: Spacing.four` it sat underneath the ~70pt tab bar; the overlap was invisible while the pill was one line and clipped its text the moment it grew.

On native, granted coords flip `properties={{ isMyLocationEnabled: true }}` on `AppleMaps.View`/`GoogleMaps.View` for the OS's own blue-dot rendering; on web, `concerts-map-leaflet.web.tsx` draws its own blue marker (deliberately blue — the conventional "you are here" colour, and distinct from the red concert pins) since Leaflet has no native equivalent. `src/lib/geo.ts`'s `distanceLabelFor()` (haversine, city-scale accuracy) computes a "2.3 mi away" label wherever a screen has both the viewer's coords and a concert's — `ConcertListCard`/`ConcertDetailSheet` take it as a precomputed optional prop rather than raw coordinates, since `ConcertSummary` deliberately excludes coordinates (see its definition in `concert.ts`).

**Get Directions.** `ConcertDetailSheet` has a "🧭 Get Directions" row, and the venue/address meta line itself is also a tappable link (underlined + accent-colored — a color change alone reads as emphasis, not necessarily "tap me") — both open the same `directionsUrl` via `Linking.openURL`. `src/lib/directions.ts`'s `getDirectionsUrl()` queries by **"Venue Name, Address" text, not raw lat/lng** — Google's own docs warn a bare coordinate shows only "a pin... but no additional place information," which read as untrustworthy/wrong-looking to users even when it's the correct spot; geocoding the real name+address resolves to the actual named place (e.g. "Barclays Center") instead. Builds an Apple Maps URL (`maps.apple.com/?daddr=<query>`) on iOS or Google's universal cross-platform URL (`google.com/maps/dir/?api=1&destination=<query>`, works as both an app deep link and a plain web fallback) elsewhere — deliberately the **long-established** `daddr=` scheme, not Apple's newer unified `/directions` endpoint, since that one requires iOS 18.4+ and would break the feature on older devices. `travelmode` is deliberately omitted from both so the user lands on the full walk/drive/transit/bike picker rather than one forced mode. Deliberately **not** built as in-app walk/drive/transit/bike time estimates — that needs a real routing API (Google Directions, Apple MapKit, etc.), which would mean either exposing a key client-side (same tradeoff as the deferred Ticketmaster key issue) or standing up a backend proxy; deep-linking to the native Maps app gets the same comparison for free, with zero added cost or key-exposure risk. Same precomputed-prop pattern as `distanceLabel` — built by the screen (which has the full `Concert`) and passed down, since `ConcertSummary` has no coordinates.

**Auth + database layer**: `src/lib/supabase.ts` (client) → `src/hooks/use-auth.ts` (session state, sign up/in/out/reset) → `src/services/{profile,saved-concerts}.ts` (Supabase CRUD, RLS-scoped to `auth.uid()`) → `src/hooks/{use-profile,use-saved-concerts}.ts` → `src/app/settings.tsx`. `signUp` distinguishes an immediate session from "confirmation email required" (`data.session` is `null` in the latter case) — the Settings screen surfaces that explicitly rather than appearing to do nothing.

**Forgot password.** Settings' sign-in form has a "Forgot password?" link (`useAuth().resetPassword(email)`, calls `supabase.auth.resetPasswordForEmail`) that emails a reset link; `src/app/reset-password.tsx` is where it lands. The Supabase client has no `flowType` set, so it defaults to auth-js's **implicit flow** — the link redirects with a `#access_token=...&refresh_token=...` hash fragment, not a `?code=` param. Since the client is also configured with `detectSessionInUrl: false` (needed so the AsyncStorage-based storage adapter doesn't choke trying to parse a URL on native), nothing auto-detects that fragment — `reset-password.tsx` parses it manually and calls `supabase.auth.setSession()` itself before showing the "choose a new password" form.

`reset-password.tsx` is a deliberately **untriggered** sibling route next to `index.tsx`/`explore.tsx`/`ask.tsx`/`settings.tsx` — Expo Router's `NativeTabs` (native) and `expo-router/ui`'s `Tabs` (web) only add a tab bar button for routes with an explicit `Trigger`; an untriggered route in the same `_layout.tsx` is still directly navigable, it just never shows as a tab. No restructuring into a `(tabs)` route group was needed for this.

**Web-only for now.** `getResetPasswordRedirectUrl()` in `use-auth.ts` computes `window.location.origin + '/reset-password'` on web (works in dev and wherever this ends up deployed, no hardcoding) — that part is live and testable. The native branch builds an `expo-linking`-based app-scheme URL, but completing the flow there needs two things this session can't do: the resulting scheme added to Supabase's **Authentication → URL Configuration → Redirect URLs allow list** in the dashboard, and a real device/dev-build to verify the deep link actually reopens the app. `reset-password.tsx` shows an explicit "only works on web for now" message on native rather than silently failing.

**Local-first caching.** `src/hooks/use-cached-resource.ts` is a generic stale-while-revalidate hook (AsyncStorage-backed): paints instantly from the last cached value, then refetches in the background and updates cache + state. Used for concerts (keyed per city), saved concerts, and profile (both keyed per user id). Reuse this rather than hand-rolling another fetch/cache hook.

**Database schema** lives in `supabase/migrations/` (plain SQL, no ORM). There is no standing Supabase CLI session — schema changes are written here as a new timestamped migration file and applied by pasting into the Supabase SQL Editor, not by running `supabase db push` (unless the user has just handed over a fresh personal access token for that).

**Web layout gotchas found the hard way** (only surfaced by screenshotting at phone width — desktop-width testing missed both):
- React Native's default `flexShrink` is `0` (unlike web CSS's `1`). A `flexGrow: 1` child with a `maxWidth` inside a row-direction parent will *not* shrink below that maxWidth on a narrow viewport — it overflows and gets clipped on both sides when the parent centers it. `ScreenScaffold`'s container uses `width: '100%'` + `maxWidth` instead of `flexGrow: 1` + `maxWidth` for exactly this reason — don't revert it.
- Leaflet's own controls (zoom buttons, etc.) use `z-index: 1000` in its default CSS. Any floating UI drawn over the web map (`concerts-map-leaflet.web.tsx`) needs a `zIndex` comfortably above that — `explore.tsx`'s overlays use `1100` — or Leaflet paints over it despite DOM order.
- **`hitSlop` does nothing on web.** React Native Web doesn't implement it on `Pressable`, so a control sized to its glyph and padded out with `hitSlop` has a tap target of exactly that glyph — the padding exists only in the source. This shipped three times: the week arrows (24×20), the date picker's month arrows (a bare glyph, ~12pt wide), and the settings back row (24pt tall, and stretched full-width as a flex child so taps far from the label still fired). All three now set real width/height against `MinTouchTarget` (44). Size touch targets with layout; treat `hitSlop` as a native-only bonus on top of an already-adequate box, never as the thing that makes one adequate.
- React Native Web stamps *every* plain `View` with its own `position: relative; z-index: 0` by default, which means every View is its own local stacking context. A child's `zIndex` only wins against siblings *within that same parent* — it can't "escape" to out-rank an unrelated part of the tree. This bit `ConcertsFilterBar`'s city dropdown twice: once trapped inside its parent (fixed by giving the filter bar's root container its own high `zIndex`), and once losing a tie against its own sibling ScrollView (fixed by giving that specific wrapper an explicit `zIndex: 1`). When a floating menu is misbehaving, check the *whole* ancestor chain's z-index/position, not just the menu's own style.

**A repo-wide ESLint rule** (`react-hooks/set-state-in-effect`, from `eslint-config-expo`) flags most `setState` calls inside `useEffect`, including indirect ones (e.g. calling a `useCallback`-wrapped async function that eventually sets state). Where the pattern is intentional and safe (e.g. fetch-on-mount), the established convention in this codebase is a targeted `// eslint-disable-next-line react-hooks/set-state-in-effect` with a one-line comment explaining why it's safe — see `use-cached-resource.ts` for an example — rather than restructuring around the rule.

**No decorative emoji in the UI.** Meta rows, buttons, and labels use typographic hierarchy instead (in the detail sheet: the date leads at full size/contrast, the address is distinct as an accent link, the distance recedes as secondary text). Emoji-as-icon is a recognisable AI-generated-UI tell, and it renders inconsistently across platforms anyway. `♥`/`♡`/`✕`/`‹`/`›`/`▾`/`•` are *typographic glyphs*, not emoji — they inherit text colour (the saved heart takes `theme.accentText`) and are fine to keep. Two things were reviewed against the same critique and **deliberately kept**: the map pin `box-shadow`s in `concerts-map-leaflet.web.tsx` (functional — they separate a 16px pin from busy *light* map tiles, not decorative depth on a dark surface) and the `expo-blur` web tab bar (translucent bottom bars are long-standing native iOS convention, and it exists to mirror the real native tab bar). `expo-glass-effect` was removed from `package.json` — it was declared but never imported.

## Follows, alerts and push — BUILT AND DEPLOYED

Undocumented here for a while, which is worse than usual for this one: it is three Edge Functions, four migrations and a cron schedule, none of it visible from the app code alone.

**Follows.** `followed_artists` / `followed_venues`, reached through `src/services/follows.ts` → `src/hooks/use-follows.ts`. Matched on **normalised names** (`followKey()` — trim, lowercase, collapse whitespace) because no source supplies a stable artist id; `20260823120000_follow_by_artist_id.sql` adds exact-id matching on top, but `addFollows` (the bulk path used by `follow-picker.tsx`) does not yet pass `artistId`, so most follows still take the name arm. Following a **venue matches every act in that room**, deliberately — a trusted room is how you meet acts you have not heard of, and that is the case artist-only discovery misses. `matchesFollows` in `use-concerts-filters.ts` is the client-side join and is tested; if it ever drifts from `followKey` the Following filter silently returns nothing forever.

**The alert engine**, in order:
`poll-concerts` (cron, every 3h) fetches each city and hands it to `ingest_concerts()`, which decides what is new and queues rows in `pending_alerts` for whoever follows it → `send-alerts` (cron, hourly) reads `alerts_due()`, respects quiet hours and a 7-day per-user cap, sends via the Expo Push API, and calls `mark_alerts_sent()` → `queue_tomorrow_alerts()` handles day-before reminders for saved shows.

Two things that bit hard and must not regress:
- **`poll-concerts` must query the same cities as the `concerts` proxy.** It once asked for `city=New York` alone while the proxy asked for all five boroughs, so Brooklyn Steel, Elsewhere, Avant Gardner and House of Yes were displayed by the app and invisible to the alert engine — a follow on any of them could never fire, silently. `poller-parity.test.ts` now compares the city lists, the genre regexes, and `isLikelyElectronic` itself.
- **Delivery is marked from tokens Expo actually accepted**, never from "no dead token was reported". A whole-chunk failure used to mark the batch delivered, which stamps `sent_at` (nothing re-queues it) and bumps `last_notified_at` (the 7-day cap) — one outage silently destroyed a batch and locked those users out for a week.

**Push tokens** (`src/services/push-tokens.ts`, `use-push-notifications.ts`) are keyed on the **token**, not the user — one account on a phone and a tablet is two devices. Registration runs on **every launch** where permission is granted and a session exists, because tokens rotate after a reinstall or restore and a stale row leaves the device unreachable once Expo retires it. `signOut` releases the token **before** `supabase.auth.signOut()`, since the delete is RLS-scoped to the session — skipping it leaves the next person on that device receiving the previous account's alerts, which name what that account follows.

`src/hooks/use-notification-routing.tsx` registers `setNotificationHandler` (without it, SDK 57's default is *not to show* a foreground notification, and the server counts it delivered anyway) and routes a tap to `/concert/[id]` from `data.concertIds`. It has a `.web.tsx` no-op stub: `useLastNotificationResponse` reaches a native method that throws on web, and from the root layout that blanks every screen.

**Shared filter state.** `src/hooks/use-filter-state.tsx` holds city, category, borough, date, week, distance and Following in one context at the tabs layout, so the list and the map are two views of one query rather than two screens that drift apart. `concert/[id]` reads the same city — it needs it to *find* the show, and giving that screen its own default meant every city except New York rendered "Show not found".

**Week membership is judged on the venue's calendar, not the viewer's.** `isWithinActiveWindow` and `isThisWeekend` compare `YYYY-MM-DD` date keys from `getConcertDateKey(startDateTime, venue zone)`. Comparing instants against device-local week boundaries made the night strip and the list contradict each other — a Sunday 9pm LA show counted on Sunday's bar and excluded from the list under it, and a show late the previous Sunday listed with no bar for it. `getWeekWindow` itself stays device-local on purpose: "which week is it now" is a question about the person holding the phone.

## Ask feature (LLM-backed) — BUILT BUT PARKED, NOT A TAB, NOT DEPLOYED

> **Status (2026-08-16):** shelved by the owner, not abandoned mid-build. The code below is complete and type-checks; it has simply never run, because the Edge Function was never deployed and the `ask_usage` migration was never applied. The tab was removed so it couldn't lead to a screen that only errors. **Do not treat the deploy steps below as outstanding work** — they're the recipe for reviving the feature, not a checklist someone forgot.

`src/app/ask.tsx` → `src/hooks/use-ask.ts` → **`supabase/functions/ask/index.ts`** (Supabase Edge Function) → Anthropic API. The Edge Function exists so the **Anthropic API key stays server-side** — an `EXPO_PUBLIC_` key ships in the client bundle, and unlike the Ticketmaster key an LLM key is *directly billable*, so an extracted one could spend against the account uncapped.

**Two grounding layers, because a model left to answer freely invents shows that don't exist.** The Edge Function sends a catalogue of the real fetched concerts and uses **structured outputs** (`output_config.format`) so the model returns `{reply, concertIds}` rather than prose containing event names. `use-ask.ts` then filters those ids against the app's *own* concert list — a hallucinated id matches nothing and renders nothing. Never replace this with "trust the reply text."

**Cost controls, all deliberate** (this endpoint bills real money per call):
- **It routes through the Perplexity Router API**, not Anthropic directly — see `.env.example`, which is the accurate copy: the secrets are `PERPLEXITY_API_KEY` and `PERPLEXITY_MODEL`, plus optional per-token costs for the spend display. This file said `claude-haiku-4-5` long after that changed. The reasoning behind the original choice still holds whatever the provider: the task is constrained selection from a supplied list rather than hard reasoning, and cost was the binding constraint, so the cheapest capable model wins. The Router API needs paid credits on the Perplexity org; without them it returns an error rather than falling back.
- **Auth required.** Without it this is an open billable proxy anyone could point a script at — this is why Ask is the one screen that gates on sign-in.
- **Per-user daily cap** (40) enforced in Postgres via `increment_ask_usage()` — an atomic upsert-and-return so two concurrent requests can't both slip past. The counter is `security definer` and revoked from `public, anon, authenticated`, so a client can't call it at all.

  That revoke was **wrong until 2026-08-29**, and this file asserted it was fine the whole time — which is exactly why nobody looked. `20260816120000` revoked `from public` only, reasoning about the PUBLIC pseudo-role; Supabase's bootstrap runs `alter default privileges ... grant all on functions to postgres, anon, authenticated, service_role`, so the function also held *explicit* grants to those two roles, and revoking from PUBLIC does not touch an explicit grant to a named role. `20260829120000_fix_ask_usage_grants.sql` fixes it. Every other security-definer function here already named all three roles; this was the one exception. **When a doc claims a protection exists, check the migration rather than the sentence.**
- `MAX_TOKENS` 700, `MAX_CONCERTS` 60, 500-char question cap.
- Actual per-question cost is returned in the response and **shown in the UI** — the user explicitly wanted spend visible rather than discovered on an invoice.
- **Prompt caching is deliberately not used**: Haiku 4.5's minimum cacheable prefix is 4096 tokens and a ~60-concert catalogue lands well under that, so `cache_control` would silently no-op.

Single-turn by design — no conversation history is replayed, so input size doesn't grow per message.

**`tsconfig.json` excludes `supabase/functions`** — Edge Functions are Deno (npm:/jsr: specifiers, `Deno` global) and fail Node/Expo type-checking. They're type-checked by the Supabase CLI at deploy. Editors will show squiggles there without a Deno extension; that's expected, not a bug.

**Deploy steps** (not automated — there's no standing Supabase CLI session): apply the `ask_usage` migration in the SQL Editor, then `supabase functions deploy ask` and `supabase secrets set ANTHROPIC_API_KEY=...`.

## Legal screens

`src/app/privacy-policy.tsx` and `src/app/terms.tsx` are untriggered routes (same pattern as `reset-password.tsx` — reachable, never a tab), linked from an "About" section in Settings that sits **outside every auth conditional** so both are reachable without an account. They share `src/components/legal-section.tsx` (`LegalSection`/`LegalText`/`LegalBullet`/`LegalBold`) so the two documents stay typographically identical.

The content is written to be *accurate to what the code actually does*, not boilerplate — worth preserving that property when editing:
- **Location never leaves the device.** Verified: `useUserLocation` coords only reach `ConcertsMap` (rendered locally) and `distanceLabelFor` (computed locally). Nothing sends them to Supabase or any API; the Ticketmaster query uses a static city name. If that ever changes, the privacy policy is wrong and must be updated first.
- **Most prices are estimates.** Only Ticketmaster prices are real (from its API `priceRanges`); every other source gets a deterministic `mockPriceLabel()`. The terms disclose this explicitly, because a user treating a mock price as an offer is the app's clearest expectation-mismatch risk.
- No ads, analytics, or tracking SDKs — true today, and the policy says so flatly.

**Two `TODO(legal)` blockers before any public release**, one in each file: `CONTACT_EMAIL` is a loud placeholder (`REPLACE_WITH_YOUR_CONTACT_EMAIL`) that must be replaced — app stores reject policies with no contact route, and it's the only channel for the data-deletion request the policy promises — and both documents need review by an actual lawyer. These were drafted by Claude and are a starting point, not legal advice; being accurate about the code is not the same as being compliant, since GDPR/CCPA obligations depend on where users are. App stores also want a *publicly hosted* policy URL, which these in-app screens don't provide on their own.

## Tests

`npm test` runs Jest (`jest-expo` preset; config is the `"jest"` block in `package.json`). Coverage is deliberately **pure functions only** — no component rendering, no hook renderers — because that's where this app's real edge cases live and it keeps the suite fast and mock-free:

- `src/lib/__tests__/geo.test.ts` — borough point-in-polygon against the **real** NYC boundary data, using five landmark venues (MSG/Barclays/Yankee Stadium/Citi Field/St. George). Asserts the *exact* match list, not just containment, which also proves boroughs don't overlap — the specific failure mode the old bounding boxes had. Plus haversine distance (with a miles-vs-kilometers guard) and label formatting.
- `src/lib/__tests__/format-date.test.ts` — the timezone logic. `getNycDateKey` must resolve a late-evening UTC instant to the *previous* NYC day, in both EDT and EST; `dateKeyFor` → `formatDateKeyLabel` must round-trip without the classic parse-as-UTC-midnight off-by-one.
- `src/hooks/__tests__/use-concerts-filters.test.ts` — week windows, including the invariant that **a weekend never splits across two week windows**, checked from every day of the week (that property is the whole reason weeks are Monday–Sunday). Also the Pop-ups month-vs-week exception and the best-effort category keyword matchers.
- `src/hooks/__tests__/use-edm-concerts.test.ts` — `dedupeConcerts` collapsing GA/VIP duplicate listings *without* collapsing multi-day festivals (the reason the dedupe key includes exact start time).
- `src/lib/__tests__/directions.test.ts` — asserts the maps URL queries by "Venue Name, Address" rather than raw coordinates. Written platform-agnostically since `getDirectionsUrl` branches on `Platform.OS`.

**`npm run check:feed` is a live-feed tripwire, deliberately outside `npm test`.** The genre filter has now been silently broken twice by Ticketmaster re-tagging its own data, with no code change on our side — both times the code was correct, the unit tests passed, and the app was wrong. Unit tests structurally cannot catch that: they assert the rule behaves as written, and it kept behaving as written while its inputs changed meaning underneath. `src/services/__tests__/feed-tripwire.live.test.ts` hits the real feed and fails when **any single act exceeds 25% of the kept listings**. That signal was chosen over a watchlist of known-bad names because names go stale the moment a residency ends, while "one act should not be a third of this app" stays true — and it doubles as the residency-flooding detector parked earlier. Verified against live data: the pre-fix rule puts Harry Styles at 36% (fires), the current rule puts Galantis at 8% (passes). It's excluded from `npm test` via `testPathIgnorePatterns` so the normal suite stays hermetic and offline. Two environment notes: it uses **`node:https`, not `fetch`**, because jest-expo swaps in Expo's `FetchResponse` polyfill which doesn't work under Jest at all (`.status` is `undefined`, `.text()` throws); and it reads `.env.local` itself, since only the Expo CLI loads that file — kept local to the file rather than in `jest.setup.js` so the rest of the suite gains no access to real credentials.

Two setup details worth knowing before adding tests:
- **`jest.setup.js`** mocks AsyncStorage with the mock that library ships. Without it, *any* test whose module graph reaches `src/lib/cache.ts` (i.e. anything importing the concert or profile hooks) dies at import with "NativeModule: AsyncStorage is null", even if the test never touches storage.
- **`tsconfig.json` sets `"types": ["jest", "node"]`.** `@types/jest` alone wasn't enough — TypeScript wasn't auto-registering the globals, so `describe`/`it`/`expect` failed to type-check. `node` is listed alongside it because setting `types` at all disables automatic `@types` inclusion, and the app reads `process.env`.

A few pure helpers in the hook files (`getWeekWindow`, `isThisWeekend`, `matchesCategory`, `isWithinActiveWindow`, `dedupeConcerts`) are exported solely so tests can reach them — they're marked with a comment saying so.
