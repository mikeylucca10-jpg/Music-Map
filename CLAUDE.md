@AGENTS.md

## Commands

- `npm run web` / `npm run ios` / `npm run android` — start the Expo dev server for a given platform (`npm start` lets you pick a platform interactively).
- `npm run lint` — ESLint via `expo lint` (flat config in `eslint.config.js`, extends `eslint-config-expo`).
- `npx tsc --noEmit` — type-check (no dedicated npm script for this).
- `npm run reset-project` — Expo's stock script to archive the starter app into `app-example/` and scaffold a blank `src/app/`. Not relevant day-to-day; only run if explicitly asked to reset the template.
- `npm test` — Jest via the `jest-expo` preset (config lives in `package.json`, not a separate file). See "Tests" below.

## Environment variables

Copy `.env.example` to `.env.local` (gitignored) and fill in real values. All are `EXPO_PUBLIC_`-prefixed so Expo inlines them client-side at build time:
- `EXPO_PUBLIC_TICKETMASTER_API_KEY` — required for the concerts feature to return real data.
- `EXPO_PUBLIC_EDMTRAIN_API_KEY` — optional; `src/services/edmtrain.ts` returns `[]` until this is set.
- `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` — required for auth/saved-concerts/profile to work; `src/lib/supabase.ts` falls back to placeholder values and `isSupabaseConfigured` gates the UI when unset.

## Architecture

This is an Expo Router (file-based routing, `src/app/`) universal app targeting iOS, Android, and web (`web.output: "static"` in `app.json`), building an NYC EDM concert finder on top of the default Expo starter template.

**Dual tab-bar implementation.** `expo-router/unstable-native-tabs` (`src/components/app-tabs.tsx`) doesn't render on web, so there's a parallel web-only tab bar (`src/components/app-tabs.web.tsx`) built from `expo-router/ui`'s `Tabs`/`TabList`/`TabTrigger`. Both are bottom bars with icon+label, matching each other — the web one uses `expo-blur`'s `BlurView` for a translucent/frosted background (it used to float as a pill at the *top*; that was deliberately moved to the bottom to match native and fix a real overflow bug — see the web layout gotchas below). Both must be updated together when adding/removing a tab/route.

**Platform-split files.** Metro resolves `*.web.tsx` over `*.tsx` on web automatically. Used for: the tab bars above, `animated-icon.web.tsx`, `use-color-scheme.web.ts`, and the concerts map (`concerts-map.tsx` for native vs `concerts-map.web.tsx`/`concerts-map-leaflet.web.tsx` for web).

**SSR gotcha:** because `web.output` is `"static"`, Expo Router does a Node-based static render pass (even in dev) with no `window`/`document`. Any module that touches those at import time crashes every route. This bit both the Leaflet map (fixed by lazy `import()`-ing `concerts-map-leaflet.web.tsx` client-side only from `concerts-map.web.tsx`, gated on `typeof window !== 'undefined'`) and the Supabase client (AsyncStorage's web backend touches `window`; `src/lib/supabase.ts` wraps it in an SSR-safe storage adapter that no-ops server-side). Keep this in mind before adding any browser-only library.

**Theming.** `src/constants/theme.ts` is dark-only by design — `Colors.light` and `Colors.dark` intentionally share one palette (this is not an adaptive light/dark app; styled after TIXR/CrowdVolt: near-black surfaces, one accent color used sparingly for active/selected states and saves, a single `Radius` scale (`card`/`large`/`pill`) instead of ad hoc corner values). `useTheme()` (`src/hooks/use-theme.ts`) resolves it.

**Two accent tokens, and they are not interchangeable.** `theme.accent` (`#E03131`) is the **fill** — pill buttons, selected chips, the selected calendar day — with `theme.accentInk` (white) as the text on top of it. `theme.accentText` (`#EF4444`, the same red lightened) is for the accent used **as** a mark on the dark background: link text, the saved-heart icon, spinners, thin outlines, the carousel dot. The split exists because a fill colour and a text colour have opposite contrast requirements — measured on `background`, `accent` only reaches ~4.4:1 (below WCAG AA for the 14px text this app uses) while `accentText` reaches 5.3:1; conversely white-on-`accent` is 4.5:1 (passes) where white-on-`accentText` would not. Rule of thumb: **behind content → `accent`; on the dark background → `accentText`.** The one deliberate exception is the Leaflet concert pin (`concerts-map-leaflet.web.tsx`), which uses `accent` because it sits on *light* map tiles, not on the app's dark ground.

The palette was violet (`#8B5CF6`) until 2026-08-15. It moved to red because the reference designs the user kept pointing at (their own TIXR/CrowdVolt-style screenshots) use a red/coral accent on black, and because "purple and black" is a widely-recognised AI-generated-design tell. `backgroundSelected` was retinted warm (`#241F1F`) at the same time so raised surfaces sit in the accent's colour family. Note the old violet actually *failed* AA for white-on-accent (4.23:1), so this was an accessibility improvement as well as an aesthetic one. **The soft `Radius` scale was deliberately kept** — rounded corners are a native-mobile platform convention (and are all over the user's own reference screenshots); the "soft corner radius" critique targets `rounded-lg`-on-everything web design and doesn't transfer here. `ThemedText`/`ThemedView` (`src/components/`) are the standard building blocks — prefer them over raw `Text`/`View` with manual colors; `ThemedText type="eyebrow"` is the bold/uppercase/letter-spaced style used for section headers ("Buy Tickets", "Saved Concerts"). `ScreenScaffold` (`src/components/screen-scaffold.tsx`) is the shared scrollable-screen shell used by List/Settings — reuse it rather than hand-rolling the header+ScrollView pattern.

**Visual design.** Image-forward cards: `ConcertListCard` renders concert poster art (`imageUrl`) with a bottom gradient overlay (`expo-linear-gradient`) and falls back to a plain themed card when a concert has no image. `SkeletonCard`/`SkeletonCardRow` (`src/components/skeleton-card.tsx`) are pulsing placeholders shown instead of spinners while concert images load. `expo-haptics` fires a light impact on every save/favorite tap.

**Concerts data layer**, in dependency order:
`src/types/concert.ts` (`Concert`; `ConcertSummary` — the display-only shape shared by cards/the detail sheet/ticket links, i.e. everything except map coordinates and filter-only fields; `City`, `CITIES`, `Borough`; `SavedConcert = ConcertSummary`) → `src/services/{ticketmaster,edmtrain}.ts` (pure fetch-and-normalize per source, both return `Concert[]`; `ticketmaster.ts`'s `pickBestImage()` picks by actual pixel area, not `images[0]` — Ticketmaster's image array isn't sorted by size, e.g. a 305×225 thumbnail can sit ahead of a 2426×1365 `_SOURCE` original in the same response) → `src/hooks/use-edm-concerts.ts` (merges sources, dedupes via `dedupeConcerts()` — same show can come back as two listings, most commonly separate GA/VIP Ticketmaster "events" for one show, keyed on name+venue+exact start time so a multi-day festival, which has a different start time per day, still shows once per day rather than being collapsed — then sorts) → `src/hooks/use-concerts-filters.ts` (client-side category filtering: This Weekend/21+/Free are real fields, Pop-ups/Festivals/Clubs/Day Parties are best-effort keyword matches; also owns borough filtering — see below) → `src/components/{concerts-filter-bar,concerts-map,concert-list-card}.tsx` → the `explore.tsx`/`list.tsx`/`index.tsx` screens. Tapping a card or map pin opens `src/components/concert-detail-sheet.tsx` (a bottom sheet), which lists tappable ticket-source rows from `src/lib/ticket-sources.ts` — Ticketmaster gets the real link/price from the API response; Vivid Seats and AXS get a confirmed direct search link (`?searchTerm=`/`?q=` respectively — AXS's verified against a live `axs.com/search?q=` example); and SeatGeek/StubHub/Dice/CrowdVolt/TIXR get a domain-scoped web-search fallback (`site:seatgeek.com ...`) with a clearly-marked mock price, since none of those five have a verifiable direct search URL (TIXR actively 403s non-browser requests via DataDome bot protection, even on its homepage) — see the `TODO(real pricing)` comment there for what real integration would need per platform.

**Multi-city support.** `CITIES` (`src/types/concert.ts`) has six RA-Guide-style major US cities — Ticketmaster can query any of them today, but **NYC is the only one actually vouched for**; the rest are there so the switcher/preference are ready. Each screen (`explore.tsx`/`list.tsx`/`index.tsx`) still owns its own local `city` state independently (unchanged), but now seeds it from the signed-in user's `profiles.default_city` via `src/hooks/use-apply-default-city.ts` — a one-time effect (latched with a ref) that applies the saved default on first load without fighting a manual city switch made afterward. Users set the preference in Settings' "Default City" chip row, which calls `updateProfile({ defaultCity })`. Concert date/time formatting (`src/lib/format-date.ts`) is still hardcoded to NYC's timezone — `City.timezone` exists but isn't wired into it yet.

**Borough filtering.** `City.boroughs?: Borough[]` (`src/types/concert.ts`) is an optional list of named sub-areas — populated for NYC (Manhattan/Brooklyn/Queens/Bronx/Staten Island), left `undefined` for cities without well-known named sub-areas (e.g. Las Vegas). Each `Borough.boundary` is a **real GeoJSON MultiPolygon** from NYC Open Data's official "Borough Boundaries" dataset (Dept. of City Planning, dataset id `gthc-hcne`, water excluded, geometry simplified to ~174KB — see `src/data/nyc-boroughs.ts` and the raw `src/data/nyc-borough-boundaries.json`), not an approximated bounding box — `src/lib/geo.ts`'s `isPointInMultiPolygon` (standard ray-casting, handles holes) tests a venue's actual lat/lng against the real borough shape. No API exposes a borough field directly, so this still filters against the venue coordinates already fetched for the map, but the geometry itself is exact, government-sourced data, verified against known venues (Madison Square Garden→Manhattan, Barclays Center→Brooklyn, Yankee Stadium→Bronx, Citi Field→Queens, St. George Theatre→Staten Island all classify correctly) — unlike the category keyword matchers, this doesn't need re-verification as venues are added. `useConcertsFilters(concerts, city)` takes `city` as a second argument and owns `selectedBoroughId`/`setBoroughId` alongside `category`/date, resetting the borough selection when `city` changes — done by comparing `city.id` during render (not in a `useEffect`), so it doesn't need a `set-state-in-effect` eslint-disable. Boroughs are **not** a separate chip row — they're nested inside the city dropdown itself (New York → Manhattan/Brooklyn/Queens/The Bronx/Staten Island, indented under the city they belong to), so picking a borough sets both `city` and `selectedBoroughId` in one tap and the city pill's label switches to show the borough name instead. Tapping the parent city row clears the borough back to "all of this city." The dropdown (`cityMenu` style) has a `maxHeight` + `ScrollView` since with boroughs nested in it can run past a screen's worth of rows.

**Date filtering.** `ConcertsFilterBar` has a "Date" pill next to the city pill (both in a `pillsRow`, label defaults to today's date rather than a generic placeholder when nothing's picked) that opens `src/components/date-picker-sheet.tsx` — a real calendar-grid bottom sheet (month navigation, SUN–SAT day grid, today outlined, selection filled in `theme.accent`, "This Week"/"Next Week" quick-select, "Reset to Today"/"Apply") rather than a scrolling list, matching a native-calendar UX pattern. Selecting a date filters to concerts on that exact NYC-calendar day, compared via `getNycDateKey()` (an `Intl.DateTimeFormat` with `timeZone: 'America/New_York'` and `en-CA` locale for a direct `YYYY-MM-DD` string) so the comparison lines up with what's actually displayed, regardless of the viewer's own device timezone. The sheet re-stages its pending selection from the applied one every time it opens (compares a `wasVisible` state during render, not a `useEffect`) so a cancelled edit doesn't leak into the next open. Calendar grid math (which weekday the 1st falls on, days in month) intentionally uses local device time — it's just day-of-week/day-count arithmetic on a `{year, month, day}` triple, not a concert-instant comparison, so no timezone conversion is needed; `dateKeyFor()`/`formatDateKeyLabel()` in `src/lib/format-date.ts` build/format keys directly from those integers. The "This Week"/"Next Week" buttons don't close the sheet on tap — "Next Week" calls the same relative `goToNextWeek` stepper as the filter bar's own `‹ ›` row (see below), so repeat taps keep paging forward instead of landing on a fixed week, and a live "Showing: …" label inside the sheet gives feedback since the modal covers the filter bar's own week label while open.

**Default week/month scoping.** Opening the app doesn't dump every upcoming show — `useConcertsFilters` also owns a `weekOffset` (default 0) that scopes results to the *current* Monday–Sunday week by default, paged via a "‹ This Week ›" row in `ConcertsFilterBar` (shown between the pills row and the footer). Weeks are Monday–Sunday specifically so a weekend (Fri/Sat/Sun) never splits across two week windows — verified against `isThisWeekend`'s own Friday-anchor math, which now also shifts by `weekOffset * 7` days so paging weeks also pages "This Weekend." **Pop-ups is the one exception**: it's scoped to the current calendar month instead of a week (pop-ups are sparse enough that a week window often comes up empty), so the week-nav row hides itself when `category === 'Pop-ups'` (`weekNavRelevant` in the hook's return). Picking a specific date via the calendar sheet overrides the week/month window entirely (but still combines with category/borough) — the week-nav row also hides itself once a date is selected, since it wouldn't do anything. Paging is capped at `MAX_WEEKS_AHEAD` (8) so the "next week" arrow can't run away indefinitely, mirroring the date picker's 12-month cap on the same idea. `useConcertsFilters` ANDs `category` (+ its week/month window), `selectedBorough`, and `dateKey` together — this is all additive to the existing category filters (This Weekend/21+/Free/etc.), not a replacement for any of them.

**Filters dropdown.** The category chips (All/This Weekend/21+/Free/Pop-ups/Festivals/Clubs/Day Parties) are **not** a horizontal scrolling chip row — like the city/borough control, they're consolidated into one "Filters ▾" pill (third pill in `pillsRow`, alongside City and Date) that opens a dropdown list, current selection highlighted. Its menu (`filtersMenu` style) opens right-aligned (`right: 0`, not `left: 0` like `cityMenu`) since it's the rightmost pill — opening from the left edge would push it off-screen on a narrow phone.

**User location + distance.** `src/hooks/use-user-location.ts` wraps `expo-location`, but gates the real OS permission dialog behind the app's own soft-ask first (`src/components/location-permission-prompt.tsx`, a "Turn On Location"/"Not Now" sheet) — standard practice since the OS dialog is much harder to reverse than an in-app one if declined reflexively. **Only `explore.tsx` renders the sheet** (list.tsx/index.tsx call the hook read-only, just to pick up coords if already granted, so switching screens before answering can't trigger a duplicate prompt). If declined or not yet granted, Explore shows a small "📍 Show My Location" pill (bottom-right of the map) to retry on demand.

What's persisted to AsyncStorage (`location-prompt-choice`) is the user's *choice* — `'declined'` (tapped "Not Now") vs `'requested'` (tapped "Turn On Location") — not a plain "have we asked" boolean, and that distinction matters: browsers offer a temporary "Allow once" grant that expires on reload, at which point `getForegroundPermissionsAsync()` correctly reports back to `'undetermined'`. A real granted/denied OS decision, or an explicit `'declined'` choice, suppresses the sheet; a lapsed "allow once" grant (`'requested'` on file but status back to `'undetermined'`) re-shows it automatically rather than silently doing nothing. `getCurrentPositionAsync` is also wrapped so a failed position fetch (timeout, `POSITION_UNAVAILABLE`) can't leave `hasPrompted` stuck at `null` forever — that would hide both the sheet and the retry pill with no way back in.

On native, granted coords flip `properties={{ isMyLocationEnabled: true }}` on `AppleMaps.View`/`GoogleMaps.View` for the OS's own blue-dot rendering; on web, `concerts-map-leaflet.web.tsx` draws its own blue marker (deliberately blue — the conventional "you are here" colour, and distinct from the red concert pins) since Leaflet has no native equivalent. `src/lib/geo.ts`'s `distanceLabelFor()` (haversine, city-scale accuracy) computes a "2.3 mi away" label wherever a screen has both the viewer's coords and a concert's — `ConcertListCard`/`ConcertDetailSheet` take it as a precomputed optional prop rather than raw coordinates, since `ConcertSummary` deliberately excludes coordinates (see its definition in `concert.ts`).

**Get Directions.** `ConcertDetailSheet` has a "🧭 Get Directions" row, and the venue/address meta line itself is also a tappable link (underlined + accent-colored — a color change alone reads as emphasis, not necessarily "tap me") — both open the same `directionsUrl` via `Linking.openURL`. `src/lib/directions.ts`'s `getDirectionsUrl()` queries by **"Venue Name, Address" text, not raw lat/lng** — Google's own docs warn a bare coordinate shows only "a pin... but no additional place information," which read as untrustworthy/wrong-looking to users even when it's the correct spot; geocoding the real name+address resolves to the actual named place (e.g. "Barclays Center") instead. Builds an Apple Maps URL (`maps.apple.com/?daddr=<query>`) on iOS or Google's universal cross-platform URL (`google.com/maps/dir/?api=1&destination=<query>`, works as both an app deep link and a plain web fallback) elsewhere — deliberately the **long-established** `daddr=` scheme, not Apple's newer unified `/directions` endpoint, since that one requires iOS 18.4+ and would break the feature on older devices. `travelmode` is deliberately omitted from both so the user lands on the full walk/drive/transit/bike picker rather than one forced mode. Deliberately **not** built as in-app walk/drive/transit/bike time estimates — that needs a real routing API (Google Directions, Apple MapKit, etc.), which would mean either exposing a key client-side (same tradeoff as the deferred Ticketmaster key issue) or standing up a backend proxy; deep-linking to the native Maps app gets the same comparison for free, with zero added cost or key-exposure risk. Same precomputed-prop pattern as `distanceLabel` — built by the screen (which has the full `Concert`) and passed down, since `ConcertSummary` has no coordinates.

**Auth + database layer**: `src/lib/supabase.ts` (client) → `src/hooks/use-auth.ts` (session state, sign up/in/out/reset) → `src/services/{profile,saved-concerts}.ts` (Supabase CRUD, RLS-scoped to `auth.uid()`) → `src/hooks/{use-profile,use-saved-concerts}.ts` → `src/app/settings.tsx`. `signUp` distinguishes an immediate session from "confirmation email required" (`data.session` is `null` in the latter case) — the Settings screen surfaces that explicitly rather than appearing to do nothing.

**Forgot password.** Settings' sign-in form has a "Forgot password?" link (`useAuth().resetPassword(email)`, calls `supabase.auth.resetPasswordForEmail`) that emails a reset link; `src/app/reset-password.tsx` is where it lands. The Supabase client has no `flowType` set, so it defaults to auth-js's **implicit flow** — the link redirects with a `#access_token=...&refresh_token=...` hash fragment, not a `?code=` param. Since the client is also configured with `detectSessionInUrl: false` (needed so the AsyncStorage-based storage adapter doesn't choke trying to parse a URL on native), nothing auto-detects that fragment — `reset-password.tsx` parses it manually and calls `supabase.auth.setSession()` itself before showing the "choose a new password" form.

`reset-password.tsx` is a deliberately **untriggered** sibling route next to `index.tsx`/`explore.tsx`/`list.tsx`/`settings.tsx` — Expo Router's `NativeTabs` (native) and `expo-router/ui`'s `Tabs` (web) only add a tab bar button for routes with an explicit `Trigger`; an untriggered route in the same `_layout.tsx` is still directly navigable, it just never shows as a tab. No restructuring into a `(tabs)` route group was needed for this.

**Web-only for now.** `getResetPasswordRedirectUrl()` in `use-auth.ts` computes `window.location.origin + '/reset-password'` on web (works in dev and wherever this ends up deployed, no hardcoding) — that part is live and testable. The native branch builds an `expo-linking`-based app-scheme URL, but completing the flow there needs two things this session can't do: the resulting scheme added to Supabase's **Authentication → URL Configuration → Redirect URLs allow list** in the dashboard, and a real device/dev-build to verify the deep link actually reopens the app. `reset-password.tsx` shows an explicit "only works on web for now" message on native rather than silently failing.

**Local-first caching.** `src/hooks/use-cached-resource.ts` is a generic stale-while-revalidate hook (AsyncStorage-backed): paints instantly from the last cached value, then refetches in the background and updates cache + state. Used for concerts (keyed per city), saved concerts, and profile (both keyed per user id). Reuse this rather than hand-rolling another fetch/cache hook.

**Database schema** lives in `supabase/migrations/` (plain SQL, no ORM). There is no standing Supabase CLI session — schema changes are written here as a new timestamped migration file and applied by pasting into the Supabase SQL Editor, not by running `supabase db push` (unless the user has just handed over a fresh personal access token for that).

**Web layout gotchas found the hard way** (only surfaced by screenshotting at phone width — desktop-width testing missed both):
- React Native's default `flexShrink` is `0` (unlike web CSS's `1`). A `flexGrow: 1` child with a `maxWidth` inside a row-direction parent will *not* shrink below that maxWidth on a narrow viewport — it overflows and gets clipped on both sides when the parent centers it. `ScreenScaffold`'s container uses `width: '100%'` + `maxWidth` instead of `flexGrow: 1` + `maxWidth` for exactly this reason — don't revert it.
- Leaflet's own controls (zoom buttons, etc.) use `z-index: 1000` in its default CSS. Any floating UI drawn over the web map (`concerts-map-leaflet.web.tsx`) needs a `zIndex` comfortably above that — `explore.tsx`'s overlays use `1100` — or Leaflet paints over it despite DOM order.
- React Native Web stamps *every* plain `View` with its own `position: relative; z-index: 0` by default, which means every View is its own local stacking context. A child's `zIndex` only wins against siblings *within that same parent* — it can't "escape" to out-rank an unrelated part of the tree. This bit `ConcertsFilterBar`'s city dropdown twice: once trapped inside its parent (fixed by giving the filter bar's root container its own high `zIndex`), and once losing a tie against its own sibling ScrollView (fixed by giving that specific wrapper an explicit `zIndex: 1`). When a floating menu is misbehaving, check the *whole* ancestor chain's z-index/position, not just the menu's own style.

**A repo-wide ESLint rule** (`react-hooks/set-state-in-effect`, from `eslint-config-expo`) flags most `setState` calls inside `useEffect`, including indirect ones (e.g. calling a `useCallback`-wrapped async function that eventually sets state). Where the pattern is intentional and safe (e.g. fetch-on-mount), the established convention in this codebase is a targeted `// eslint-disable-next-line react-hooks/set-state-in-effect` with a one-line comment explaining why it's safe — see `use-cached-resource.ts` for an example — rather than restructuring around the rule.

**No decorative emoji in the UI.** Meta rows, buttons, and labels use typographic hierarchy instead (in the detail sheet: the date leads at full size/contrast, the address is distinct as an accent link, the distance recedes as secondary text). Emoji-as-icon is a recognisable AI-generated-UI tell, and it renders inconsistently across platforms anyway. `♥`/`♡`/`✕`/`‹`/`›`/`▾`/`•` are *typographic glyphs*, not emoji — they inherit text colour (the saved heart takes `theme.accentText`) and are fine to keep. Two things were reviewed against the same critique and **deliberately kept**: the map pin `box-shadow`s in `concerts-map-leaflet.web.tsx` (functional — they separate a 16px pin from busy *light* map tiles, not decorative depth on a dark surface) and the `expo-blur` web tab bar (translucent bottom bars are long-standing native iOS convention, and it exists to mirror the real native tab bar). `expo-glass-effect` was removed from `package.json` — it was declared but never imported.

## Legal screens

`src/app/privacy-policy.tsx` and `src/app/terms.tsx` are untriggered routes (same pattern as `reset-password.tsx` — reachable, never a tab), linked from an "About" section in Settings that sits **outside every auth conditional** so both are reachable without an account. They share `src/components/legal-section.tsx` (`LegalSection`/`LegalText`/`LegalBullet`/`LegalBold`) so the two documents stay typographically identical.

The content is written to be *accurate to what the code actually does*, not boilerplate — worth preserving that property when editing:
- **Location never leaves the device.** Verified: `useUserLocation` coords only reach `ConcertsMap` (rendered locally) and `distanceLabelFor` (computed locally). Nothing sends them to Supabase or any API; the Ticketmaster query uses a static city name. If that ever changes, the privacy policy is wrong and must be updated first.
- **Most prices are estimates.** Only Ticketmaster prices are real (from its API `priceRanges`); every other source gets a deterministic `mockPriceLabel()`. The terms disclose this explicitly, because a user treating a mock price as an offer is the app's clearest expectation-mismatch risk.
- No ads, analytics, or tracking SDKs — true today, and the policy says so flatly.

**Two `TODO(legal)` blockers before any public release**, one in each file: `CONTACT_EMAIL` is a loud placeholder (`REPLACE_WITH_YOUR_CONTACT_EMAIL`) that must be replaced — app stores reject policies with no contact route, and it's the only channel for the data-deletion request the policy promises — and both documents need review by an actual lawyer. These were drafted by Claude and are a starting point, not legal advice; being accurate about the code is not the same as being compliant, since GDPR/CCPA obligations depend on where users are. App stores also want a *publicly hosted* policy URL, which these in-app screens don't provide on their own.

## Tests

`npm test` runs Jest (`jest-expo` preset; config is the `"jest"` block in `package.json`). Coverage is deliberately **pure functions only** — no component rendering, no hook renderers — because that's where this app's real edge cases live and it keeps the suite fast and mock-free:

- `src/lib/__tests__/geo.test.ts` — borough point-in-polygon against the **real** NYC boundary data, using five landmark venues (MSG/Barclays/Yankee Stadium/Citi Field/St. George). Asserts the *exact* match list, not just containment, which also proves boroughs don't overlap — the specific failure mode the old bounding boxes had. Plus haversine distance (with a miles-vs-kilometers guard) and label formatting.
- `src/lib/__tests__/format-date.test.ts` — the timezone logic. `getNycDateKey` must resolve a late-evening UTC instant to the *previous* NYC day, in both EDT and EST; `dateKeyFor` → `formatDateKeyLabel` must round-trip without the classic parse-as-UTC-midnight off-by-one.
- `src/hooks/__tests__/use-concerts-filters.test.ts` — week windows, including the invariant that **a weekend never splits across two week windows**, checked from every day of the week (that property is the whole reason weeks are Monday–Sunday). Also the Pop-ups month-vs-week exception and the best-effort category keyword matchers.
- `src/hooks/__tests__/use-edm-concerts.test.ts` — `dedupeConcerts` collapsing GA/VIP duplicate listings *without* collapsing multi-day festivals (the reason the dedupe key includes exact start time).
- `src/lib/__tests__/directions.test.ts` — asserts the maps URL queries by "Venue Name, Address" rather than raw coordinates. Written platform-agnostically since `getDirectionsUrl` branches on `Platform.OS`.

Two setup details worth knowing before adding tests:
- **`jest.setup.js`** mocks AsyncStorage with the mock that library ships. Without it, *any* test whose module graph reaches `src/lib/cache.ts` (i.e. anything importing the concert or profile hooks) dies at import with "NativeModule: AsyncStorage is null", even if the test never touches storage.
- **`tsconfig.json` sets `"types": ["jest", "node"]`.** `@types/jest` alone wasn't enough — TypeScript wasn't auto-registering the globals, so `describe`/`it`/`expect` failed to type-check. `node` is listed alongside it because setting `types` at all disables automatic `@types` inclusion, and the app reads `process.env`.

A few pure helpers in the hook files (`getWeekWindow`, `isThisWeekend`, `matchesCategory`, `isWithinActiveWindow`, `dedupeConcerts`) are exported solely so tests can reach them — they're marked with a comment saying so.

## Known open items (deferred until closer to launch)

A security audit (2026-08-13) deferred three items on purpose — don't build these proactively:
- **Ticketmaster key exposure**: `EXPO_PUBLIC_TICKETMASTER_API_KEY` ships in the client bundle. Fix is a backend proxy (Supabase Edge Function), not a config change.
- **Bot protection on signup/signin**: needs a Supabase Dashboard toggle (not `supabase/config.toml`, which is local-dev-only), an hCaptcha/Turnstile account, and a `WebView`-based widget in the app — no native RN CAPTCHA widget exists.
- **`profiles` column-level write protection**: the UPDATE RLS policy checks row ownership but not which columns are written. Not exploitable today (no privileged field exists), but revisit immediately if one is ever added (e.g. `is_admin`).
